## 1. Leonardo Mendes Jorge Soares (`Leonardo-m-web`)

| Campo | Descrição |
|---|---|
| **Ferramenta e modelo** | ChatGPT (OpenAI), via interface de chat. |
| **Etapa: Validação de email duplicado** | Solicitei à IA que implementasse uma validação para impedir que o mesmo email fosse cadastrado mais de uma vez na mesma atividade, uma vez que a rota de registro não possuía essa verificação. |
| **Etapa: Diagnóstico e planejamento** | A IA analisou o código existente (`RegistrationService.java`, `RegistrationRepository.java`, `RegistrationController.java`) e identificou os pontos necessários para a implementação da validação, considerando a estrutura do projeto e os padrões já utilizados. |
| **Etapa: Implementação** | - Criação do método `existsByActivityIdAndStudentEmail` no `RegistrationRepository.java` para consultar se já existe um registro com aquele email para a atividade específica.<br>- Adição da validação no método `register` do `RegistrationService.java`, lançando uma exceção personalizada caso o email já esteja cadastrado.<br>- Criação da classe `EmailAlreadyRegisteredException` para representar essa regra de negócio.<br>- Adição do handler no `GlobalExceptionHandler.java` para capturar a exceção e retornar status HTTP 409 (Conflict) com a mensagem "Email já foi cadastrado na atividade". |
| **Etapa: Revisão** | A IA revisou o código modificado para garantir que a integração com o fluxo existente estivesse correta, confirmando que os demais métodos e funcionalidades não foram afetados. |
| **Principais prompts/objetivos** | - "existe uma rota que registra um usuário em uma atividade mas ela não está validando se a atividade já possui um email igual ao enviado e eu preciso dessa validação"<br>- "na parte da exceção use a normal, eu só quero que a mensagem 'email já foi cadastrado na atividade' e o status code sejam enviados"<br>- "esse é o RegistrationService, como fica com a validação?"<br>- "esse é o GlobalExceptionHandler, como fica?" |
| **Sugestões aceitas** | - A estrutura da validação utilizando o método `existsByActivityIdAndStudentEmail` do Spring Data JPA, por seguir o padrão de nomenclatura que gera queries automaticamente.<br>- O uso de `ResponseStatusException` com status `HttpStatus.CONFLICT` para retornar a mensagem de erro de forma simples e direta, conforme solicitado.<br>- A sugestão de posicionar a validação antes das demais verificações (atividade fechada, atividade lotada) para garantir que a verificação de email duplicado tenha prioridade e evite processamento desnecessário. |
| **Sugestões adaptadas** | A implementação inicial sugeria criar uma exception personalizada e um handler específico. No entanto, para manter a simplicidade, optei por utilizar `ResponseStatusException`, que já atende ao requisito sem a necessidade de criar novas classes. |
| **Revisão e validação** | A implementação foi revisada através da leitura do código modificado, verificando que a validação foi inserida no local correto e que a mensagem de erro retornada está conforme solicitado. Foram realizados testes manuais via requisições à API para confirmar que:<br>1. O primeiro cadastro com um email em uma atividade é bem-sucedido (status 201).<br>2. Uma segunda tentativa com o mesmo email para a mesma atividade retorna status 409 com a mensagem "Email já foi cadastrado na atividade".<br>3. O mesmo email pode ser cadastrado em atividades diferentes sem conflito.<br><br>Nenhum teste automatizado foi quebrado com a alteração, uma vez que a validação é uma nova regra de negócio e não interfere nas validações já existentes. |

## 3. Julia Michetti (`juliaagainagain`)

| Campo | Descrição |
|---|---|
| **Ferramenta e modelo** | Claude (Anthropic), via interface de chat. |
| **Etapa: Configuração do ambiente** | Apoio na configuração de `JAVA_HOME` no Windows e organização dos comandos de execução do backend (Maven Wrapper) e frontend (Vite) que estava dando erro e eu não entendi o porquê. |
| **Etapa: Organização do Git** | Eu pedi para ela criar os nomes para não ter que ficar pensando neles muito tempo. |
| **Etapa: Investigação e descoberta dos bugs** | Rodei a suíte de testes automatizados do backend (`./mvnw test`) e usei o apoio da IA para interpretar a saída. Isso revelou dois testes falhando, que usei para identificar e nomear os problemas:<br>- `shouldReturn404ForUnknownActivity` → atividade inexistente retornava `500` em vez de `404`.<br>- `shouldPreventRegistrationWhenActivityIsFull` → atividade lotada aceitava nova inscrição (retornava `201` em vez de `409`). |
| **Etapa: Diagnóstico de bug** | Leitura assistida do código-fonte (`RegistrationService.java`, `Activity.java`, `GlobalExceptionHandler.java`) para localizar a causa raiz do bug de inscrição em atividade lotada: ausência de validação de capacidade/status antes de persistir a inscrição. |
| **Etapa: Implementação** | - Criação da classe `RegistrationNotAllowedException`.<br>- Adição de um handler em `GlobalExceptionHandler` para traduzir essa exceção em resposta `409 Conflict`.<br>- Adição da validação de capacidade/status em `RegistrationService.register()`.<br>- Adição de `maxLength` nos campos de nome e e-mail em `RegistrationForm.tsx`, alinhando o frontend aos limites já validados pelo backend (`@Size(max = 100)` e `@Size(max = 160)`). |
| **Etapa: Revisão** | Apoio na leitura da saída dos testes após a correção, confirmando que `shouldPreventRegistrationWhenActivityIsFull` passou a ser aprovado. |
| **Principais prompts/objetivos** | - "Por que o contador de inscritos não atualiza?"<br>- "Me ajude a rodar e interpretar os testes do backend?"<br>- "Aponta pra mim os erros que os testes revelaram."<br>- "Corrija o bug de inscrição em atividade lotada seguindo o padrão do projeto, e me diga o que mudou para eu validar aqui depois."<br>- "O e-mail aceita muitos caracteres, isso precisa ser validado?" |
| **Sugestões aceitas** | - A estrutura da exceção de negócio (`RegistrationNotAllowedException`) e do handler HTTP, por seguirem o mesmo padrão já usado no projeto para `IllegalArgumentException`.<br>- A validação de `maxLength` no frontend, por já existir validação equivalente no backend (evitando divergência de regra entre as camadas). |
| **Sugestões adaptadas** | Mensagens de erro, nomes de branch e de commit foram ajustados manualmente por mim para seguir a convenção já usada pelo restante da equipe. |
| **Revisão e validação** | Cada bug foi encontrado e nomeado por mim a partir da leitura da saída real dos testes automatizados, relacionando as falhas às regras de negócio descritas no `PROJECT.md`. As mudanças de código sugeridas pela IA foram lidas e compreendidas por mim antes de serem aplicadas. A correção do bug de capacidade foi validada rodando `./mvnw test` antes e depois da mudança, confirmando que o teste relacionado passou a ser aprovado sem quebrar os demais testes que já passavam. A limitação de caracteres no formulário foi validada visualmente no navegador. |
| **Responsabilidade** | Declaro que compreendi, revisei e validei todo o conteúdo gerado com apoio de IA antes de incluí-lo neste repositório, e me responsabilizo integralmente pelo código e pelas decisões técnicas aqui entregues. |
